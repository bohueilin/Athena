## Research question
How can enterprise infrastructure-management agents built on the Model Context Protocol (MCP) be secured against agentic, multi-step attacks (prompt injection, tool poisoning, command injection, privilege escalation) using natural-language policies enforceable by non-technical domain experts?

## Problem definition
MCP has become the de facto standard letting LLMs act on external systems/infrastructure, but it introduces command injection, credential exposure, tool poisoning, and prompt injection that perimeter defenses and static ACLs cannot handle. Existing guardrails (Llama Guard, NeMo Guardrails, ShieldLM) do content moderation with fixed taxonomies / binary outputs or require proprietary scripting (Colang) / Python validators — inadequate for context-dependent, quantitative infrastructure policies and inaccessible to compliance/ops experts. Cited evidence: a study of 1,899 open MCP servers found 7.2% general and 5.5% MCP-specific tool-poisoning vulnerabilities; 61% of orgs report major cloud breaches.

## System or model being studied
InfrastructureSentinel: security middleware around Agent–MCP–Infrastructure flows, built on a dedicated **Guardian LLM** plus four interception layers, prototyped on internal HPE HPC infra (GreenLake Compute Ops Management, HPE Performance Cluster Manager).

## Threat model
- Adversary objective: subvert an infrastructure agent to run unauthorized/destructive operations, escalate privileges, exfiltrate credentials/data, or exhaust resources.
- Adversary knowledge: ranges from direct prompt-crafting to embedding instructions in external data the agent ingests (indirect); some attacks are adaptive (paper cites adaptive attacks bypassing prior IPI defenses).
- Adversary access: user prompt channel; poisoned external data sources (documents, logs, web); malicious/masquerading third-party MCP tools.
- Adversary capabilities: direct prompt injection/jailbreak, indirect prompt injection, context/memory manipulation (fake "emergency maintenance"), insecure tool use / command injection (e.g., run_script('../etc/passwd')), privilege escalation, tool poisoning / supply-chain, credential & token exposure, DoS.
- Attacker budget: not quantified.
- Phase: inference/runtime (live operational environment).
- Targeted / untargeted: targeted (infrastructure actions).
- Digital / physical: digital (data-center infrastructure).
- Adaptive / non-adaptive: acknowledges adaptive attacks; the system aims for defense-in-depth so a threat missed at one layer is caught by another.

## Trust assumptions
Trusts a Guardian LLM to correctly interpret natural-language policies and reason over context (user role, timing/maintenance windows, conversation history, system health). Assumes access to authenticated user roles, real-time system state, and the ability to intercept the agent's plan and tool calls. Policies may live in regulations, corporate manuals, or undocumented best practice — the Guardian LLM is trusted to operationalize them.

## Attack or failure mechanism
The end-to-end flow (prompt → agent reasoning → tool planning → MCP-brokered execution → state change) exposes multiple points; a successful initial attack can corrupt the agent's plan/state and cascade (compromised tools, bad info, flawed decisions), amplifying risk — motivating intervention at every stage of the reasoning-action loop.

## Proposed defense or method
Four context-aware interception layers mirroring the agent's cognitive cycle: **Layer 1 Input Filtering** (Guardian LLM semantic analysis of the user message → Safe/Unsafe + confidence + reasoning, using role, time, history, health); **Layer 2 Tool Selection Validation** (intercepts the proposed tool-call plan; blocks disallowed tools, risky combinations, privilege-exceeding actions, given env state e.g. dev vs prod); **Layer 3 Runtime Execution Gating** (final Go/No-Go immediately before MCP invocation, re-checking live system state, locks, race conditions); **Layer 4 Post-Action Auditing & Learning** (immutable human-readable audit trail of the full event chain; anomaly detection; feedback loop to refine policy interpretation/thresholds). Natural-language policy interpretation "democratizes" rule authoring; performance mitigations: intelligent caching of deterministic checks, asynchronous processing of non-critical/audit checks.

## Datasets and benchmarks
No public benchmark; a small hand-crafted scenario suite. Two attack scenarios described: (1) prompt injection (direct jailbreak, indirect via retrieved documents, context manipulation); (2) illicit tool execution (low-privilege user invoking admin-only tools, etc.). Prototype evaluation on internal HPE HPC infrastructure with domain-expert-crafted scenarios.

## Evaluation methodology
Compare three configurations — No Guardrail, LLM-as-Filter, InfrastructureSentinel — on Attack Detection Rate (ADR) across five attack classes; qualitative walk-through of multi-layer interception; internal deployment testing.

## Metrics
Attack Detection Rate (ADR, %). Table 1 (author-reported, threshold-style): Direct Prompt Injection 5 / 60 / >90; Indirect Prompt Injection 2 / 25 / >85; Tool Poisoning 10 / 15 / >88; Command Injection 15 / 50 / >76; Contextual Policy Violation 0 / 20 / >50 (No Guardrail / LLM-as-Filter / InfrastructureSentinel).

## Main findings
- Author claim: InfrastructureSentinel substantially raises ADR over both baselines across all five attack classes, with the largest gains on prompt-injection and tool-poisoning.
- Author claim: multi-layer, context-aware, natural-language policy enforcement catches threats that single-point I/O filters miss, while providing explainable confidence scores and immutable audit trails for governance/compliance.
- Author claim: viability confirmed via initial testing on internal HPE HPC infra (COM, HPCM) prototype MCP servers.

## Negative results
Even InfrastructureSentinel's reported ADR is modest for the hardest classes — Contextual Policy Violation only >50% and Command Injection only >76% — i.e., substantial residual miss rates the authors do not claim to eliminate.

## Limitations stated by the authors
Adds marginal latency from extra Guardian-LLM inference (argued acceptable for high-stakes ops, mitigated by caching/async). Future work notes needed: automated policy discovery, formal verification for guarantees about Guardian-LLM adherence, and a stronger Layer-4 feedback loop for zero-day response — implying current guarantees are absent.

## Additional limitations identified during review
_(reviewer synthesis — clearly not author claims)_
- ADR reported as coarse ">X%" thresholds with no dataset size, false-positive rate, per-scenario detail, statistical treatment, or public artifacts — evaluation is illustrative, not rigorous.
- The Guardian LLM is itself an LLM subject to prompt injection; using an LLM to defend an LLM agent creates a potentially injectable trust anchor not stress-tested against adaptive attacks (which the paper itself cites as breaking prior defenses).
- No adaptive/red-team attacker specifically targeting the four layers is evaluated.
- "Immutable audit trail" and confidence scores are asserted but their integrity/tamper-resistance mechanisms are not specified.
- Natural-language policy interpretation may be ambiguous/inconsistent; policy-to-enforcement fidelity is unmeasured.

## Design implications
A defense-in-depth guardrail aligned to the agent cognitive cycle (Perception→Planning→Action→Memory) is a strong architectural template: place enforcement at input, tool-plan, execution-gate, and audit stages so a single bypass is not catastrophic. Context (role, time, environment state, system health) should be first-class inputs to every gate — capability is not permission.

## Implementation implications
Pre-execution tool-plan validation (Layer 2) plus a just-before-invocation re-check (Layer 3) directly counter tool poisoning, privilege escalation, and race-condition/state-drift risks that content filters miss; cache deterministic role/policy checks and run auditing asynchronously to bound latency.

## Evaluation implications
Guardrail claims must report false-positive/operational-agility costs and be tested against adaptive indirect-prompt-injection, not just static scenarios; coarse ADR thresholds are insufficient evidence of protection.

## Deployment implications
Positioned for enterprise MCP infrastructure agents where audit trails and explainability satisfy governance/regulatory needs; residual miss rates (esp. contextual policy violations) mean it should gate, not replace, least-privilege credential scoping and human approval for destructive ops.

## Monitoring and incident implications
Layer-4 immutable, human-readable audit trails provide per-action decision provenance for forensics and compliance; anomaly detection (expected-success-but-failed, output deviation) feeds a policy-refinement loop — a concrete evidence-logging + runtime-monitoring pattern.

## Applicability boundaries
Directly about **MCP/agent/tool security** (core). Findings are architecture-level and demonstrated only on internal HPE HPC scenarios; the specific ADR numbers should not be generalized, and the design's security depends on the (untested) robustness of the Guardian LLM to injection.
