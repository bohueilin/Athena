## Research question
Can potential safety vulnerabilities in **non-natural-language domains** (mathematical equation solving and code completion) be exploited to jailbreak safety-aligned LLMs, and does combining multiple such strategies outperform single-strategy attacks?

## Problem definition
Most existing jailbreak attacks operate at the natural-language level and rely on a single strategy (role-play, encoding), limiting effectiveness because safety alignment has already been heavily invested in the natural-language domain. The paper reframes a malicious query as a cross-domain task so the model focuses on task completion rather than safety constraints.

## System or model being studied
Black-box commercial and open LLMs accessed via official APIs at default temperature: GPT-3.5-Turbo, GPT-4, GPT-4-Turbo, GPT-4o, GPT-4o-mini, Llama-3.1-405B; plus five "state-of-the-art" models GPT-4.1, Claude 3.7, DeepSeek-R1, Gemini-1.5-Pro, Grok-3.

## Threat model
- Adversary objective: elicit harmful/restricted content (targeted to a specific malicious query) from an aligned LLM.
- Adversary knowledge: **black-box** — only API interaction; the paper argues white-box attacks (e.g., GCG) are infeasible on closed commercial models.
- Adversary access: standard API query access; **single query** per malicious goal.
- Adversary capabilities: craft a two-module prompt (equation module: decompose query into Subject B + Tool C + unknown Execution Steps x, B+C+x=A; code module: embed into a Python `Solver` class requiring the LLM to complete `solve`).
- Attacker budget: one query per prompt (author-emphasized "single query"); no gradient access, no iterative optimization.
- Phase: inference.
- Targeted / untargeted: targeted (specific harmful instruction).
- Digital / physical: digital.
- Adaptive / non-adaptive: non-adaptive to any specific deployed defense; it is a fixed prompt-construction pipeline.

## Trust assumptions
Assumes the model treats mathematized/code-wrapped tasks as benign and prioritizes syntactic/logical task completion over semantic safety review (the "mismatched generalization" / long-tail-distribution hypothesis from Wei, Haghtalab, Steinhardt 2023). Assumes no external input/output guardrail (e.g., Llama Guard) is applied — the attack targets the model's own alignment only.

## Attack or failure mechanism
Two synergistic modules: (1) **Equation module** transforms the malicious query A into a textual equation B+C+x=A, prompting the model to "solve for x" (the concrete execution steps), obfuscating intent and bypassing input-level semantic filters; (2) **Code module** embeds A, B, C into a benign-looking `Solver` class and instructs the model (via comments) to complete the `solve` function and describe the malicious tool, redirecting attention to code correctness. The failure is safety-alignment's inability to recognize harmful intent once it is encapsulated in cross-domain (math+code) representation.

## Proposed defense or method
None — this is an offensive paper. It proposes the **attack** (EquaCode) and offers the finding as an empirical insight for future defense against advanced multi-strategy jailbreaks.

## Datasets and benchmarks
- AdvBench (Zou et al. 2023): 520 malicious queries (main results). Ablation uses a 50-query subset.

## Evaluation methodology
Single run per method. ASR judged by an LLM evaluator ("GPT-ASR" = GPT-4) scoring responses 1–10; only a score of 10 counts as success; evaluation prompt adapted from Chao et al. 2023 / Liu et al. 2025. Baseline numbers for 15 competing attacks are taken from FlipAttack (Liu et al. 2025), not re-run. Ablation uses open-source LLaMA-3.1-70B as evaluator ("LLaMA-ASR") to reduce cost, on the 50-query subset; a simplified STSA (Subject-Tools-Steps, natural-language only) baseline isolates the contribution of the equation/code encapsulation.

## Metrics
Attack Success Rate (ASR): proportion of harmful queries eliciting a compliant, query-relevant malicious response (evaluator score = 10).

## Main findings
- Author-claimed average ASR 91.19% on the GPT series and 97.62% across the five SOTA LLMs (GPT-4.1 100, Grok-3 100, DeepSeek-R1 95.96, Gemini-1.5-Pro 99.04, Claude 3.7 93.08), all with a single query.
- Per-model (Table 1, GPT-ASR): GPT-4 91.92, GPT-4-Turbo 98.46, GPT-3.5-Turbo 97.12, GPT-4o 87.12, GPT-4o-mini 81.35, Llama-3.1-405B 17.88; overall best average ASR 78.98% across the six targets.
- On GPT-4o-mini it outperforms the second-best baseline by ~10%.
- Ablation: the combined equation+code approach outperforms either module alone and the STSA natural-language baseline — author claim of a "synergistic amplification effect."

## Negative results
- Llama-3.1-405B shows low ASR across ALL methods (EquaCode 17.88), indicating comparatively strong safety alignment; the authors state considerable room remains for improving attacks against it. On GPT-4o and Llama-3.1-405B EquaCode ranks third and second (not first).

## Limitations stated by the authors
- Effectiveness against strongly-aligned models (Llama-3.1-405B) is limited.
- Ethics: they evaluated only on commercial closed-source LLMs, did not inject malicious content or leave persistent artifacts.

## Additional limitations identified during review
_(reviewer synthesis — clearly not author claims)_
- **Single-run** results with an **LLM-as-judge** (GPT-4) evaluator introduce measurement variance and potential evaluator bias/circularity (GPT-4 judging GPT-family outputs); no human validation of harmfulness reported.
- No evaluation against any deployed guardrail (input/output filtering such as Llama Guard, moderation endpoints); real API stacks may catch code/equation-wrapped harmful output at the output stage.
- Baselines are re-used from FlipAttack rather than re-implemented, so cross-method comparability depends on that prior work's harness.
- "State-of-the-art" model version identifiers (e.g., Claude 3.7, Gemini-1.5-Pro) and dates are not fully pinned; ASR against frontier reasoning models may shift with model updates.
- No measurement of output *quality/actionability* of harmful content beyond the binary judge score.

## Design implications
Safety alignment concentrated on natural-language surface forms leaves a **cross-domain / long-tail gap**: math- and code-encapsulated requests can smuggle harmful intent past semantic filters. Defenses should reason about task *intent* across representation transforms, not just surface tokens.

## Implementation implications
Deployers relying solely on model-internal alignment are exposed; independent **output-side** review (does the produced code/steps actually enable harm?) and intent-normalization (de-obfuscating math/code wrappers before the safety check) are warranted. Code-generation surfaces deserve dedicated harmful-content screening.

## Evaluation implications
Jailbreak robustness suites should include cross-domain/multi-strategy transforms (equation+code), not only role-play/encoding. LLM-judge ASR should be paired with human spot-checks and multi-run variance reporting.

## Deployment implications
A single benign-looking API call can extract harmful procedural content from most tested frontier models; rate-limiting alone is ineffective because the attack needs only one query. Stronger-aligned large models (Llama-3.1-405B) resisted better, suggesting alignment scale/depth matters.

## Monitoring and incident implications
Monitor for prompts that wrap requests in symbolic "solve-for-x" equations or `Solver`-class code-completion scaffolds around sensitive nouns/tools; log and review code-completion outputs that assemble step lists. Treat single-shot high-confidence completions of "unknown steps" as a signal.

## Applicability boundaries
Findings apply to text-in/text-out aligned LLM chat/completion APIs. They generalize to any deployment where only model-internal alignment guards the output. They should NOT be read as evidence about systems with layered input/output guardrails (untested here), nor as claims of a universal bypass — one strongly-aligned model largely resisted. Not about multimodal, tool-calling, or agentic pipelines specifically (though the code-completion vector is relevant to code agents).
