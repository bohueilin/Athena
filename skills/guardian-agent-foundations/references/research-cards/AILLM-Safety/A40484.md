## Research question
How can an LLM-based Natural Language Interface to Database (NLIDB) be aligned to **prevent privacy leakage — including stealthy multi-turn inference-based attacks — without degrading SQL-generation reliability**, and without human-annotated preference data?

## Problem definition
LLM-NLIDBs may unintentionally expose confidential database contents or be manipulated to exfiltrate data via seemingly benign query sequences. Rule-based/heuristic and LLM-agent defenses fail against **inference-based attacks** (e.g., complementary queries that are each safe in isolation but jointly reveal protected data), suffer high false positives, and can break SQL reliability. Three core challenges: Stealthy Risk (leakage only visible when responses are analyzed collectively), Pattern Coupling (risk arises from interaction of history + current query + schema constraints), and Capability Balance (security must not degrade NLIDB utility).

## System or model being studied
An LLM NLIDB that, given database schema D, predefined natural-language security constraints C, interaction history H, and current question Q, must decide Safe(x) then either generate SQL or reject (⊥). The framework (SafeNLIDB) is trained via data synthesis + preference optimization on open-source LLMs. (Model Context Protocol / tool-invocation framing is referenced as motivating context.)

## Threat model
- Adversary objective: exfiltrate/infer sensitive database records that predefined constraints prohibit.
- Adversary knowledge: black-box interaction with the NLIDB; knows enough schema/semantics to craft correlated queries.
- Adversary access: multi-turn NL query access to the interface; observes returned SQL/results.
- Adversary capabilities: **Direct Attack** (overtly request protected data) and **Inference-Based Attacks** — 9 unsafe patterns including Complementary Query (CQ), Progressive Targeting (PT), Boundary Probing (BP), Aggregation Inference (AI), and Prompt Injection (PI).
- Attacker budget: multiple benign-looking turns; no model access.
- Phase: inference / deployment (attack); the defense also acts at training (alignment) and inference (rejection decision).
- Targeted / untargeted: targeted (specific sensitive fields/rows).
- Digital / physical: digital.
- Adaptive / non-adaptive: the synthesized attack-pattern pool is fixed; not shown to be tested against an adaptive attacker that knows SafeNLIDB's detector.

## Trust assumptions
Assumes predefined per-database security constraints C (column-level, row-level, hybrid row-column) are available and correct. Assumes an open-source LLM can be fine-tuned to internalize constraint-aware refusal + reliable SQL. Trusts the synthesized data pipeline (self-generated malicious/benign interaction pairs) and the SQL executor + safety verifier used to partition preferences.

## Attack or failure mechanism
Inference leakage accumulates across turns: e.g., "list all students" (names) plus "list healthy students" (disability IS NULL) allows set-difference to deduce which named students have a disability — each query safe in isolation, jointly a violation. Conventional token-level keyword filtering and static access rules miss this context-dependent, coupled risk.

## Proposed defense or method
**SafeNLIDB** — two modules:
1. **Security-Aware Data Synthesis** (no manual annotation): discover privacy-security constraints from synthetic databases (SynSQL-2.5M); build a malicious interaction-pattern pool (9 patterns) by relating SQL syntax to constraints; synthesize malicious (unsafe) and benign (soft-safe via counterfactual rewrite; hard-safe from unrelated harmless data) SQL sets; convert SQL→NL with two-stage execution-consistency verification; assemble multi-turn samples; build a **Hybrid Chain-of-Thought (H-CoT)** = Safety-CoT + SQL-CoT with semantic-consistency filtering (Sentence-BERT cosine agreement).
2. **Alternating Preference Optimization (APO)** over DPO: a **reasoning warm-up** (SFT on H-CoT) establishes preliminary safety + SQL capability; then APO auto-partitions preferences using a safety verifier (label match) and SQL executor (execution-equivalence), anchoring correct reasoning segments and alternating optimization to mitigate DPO's multi-preference oscillation. Yields the **ShieldSQL** benchmark as a by-product.

## Evaluation methodology
Train on synthesized H-CoT data via reasoning warm-up (SFT) then APO; evaluate end-to-end defense (security) and SQL reliability against direct and inference-based attacks, comparing to larger LLMs and multi-stage baselines. APO generates N candidates per sample, verifies safety-label consistency and SQL execution-equivalence to form chosen/rejected pairs.

## Additional limitations identified during review
_(reviewer synthesis — clearly not author claims)_
- Relies on **predefined, correct security constraints C**; the framework does not discover unknown sensitive-attribute correlations at runtime beyond the constrained set, so novel inference paths outside C may still leak.
- **Self-generated attack pattern pool (9 patterns)** and self-generated benchmark (ShieldSQL) risk train/test distributional coupling; not shown against an **adaptive attacker** aware of the SafeNLIDB detector.
- Uses synthetic databases (SynSQL-2.5M) rather than real enterprise schemas; real-world constraint complexity and false-positive behavior may differ.
- APO's preference partition depends on the safety verifier's own accuracy; verifier errors propagate into training signal.
- Security vs reliability trade-off is claimed favorable but the numeric operating point is not visible in the extracted text.

## Design implications
Privacy defense for LLM-DB tools must be **context- and history-aware**: safety decisions should jointly reason over schema constraints + interaction history + current query, not per-utterance keywords. Encoding *explicit security reasoning* (Safety-CoT) alongside SQL generation lets one model both refuse leaky requests and produce correct queries.

## Implementation implications
Synthetic-data + preference-optimization pipelines can align NLIDB models without costly human annotation, using execution-equivalence and a safety verifier as automatic preference signals. Alternating optimization helps when two objectives (safety refusal vs SQL correctness) conflict under DPO.

## Evaluation implications
NLIDB security benchmarks should include multi-turn inference attacks (complementary/progressive/aggregation queries), not only direct harmful requests, and should jointly report leakage prevention AND SQL reliability (over-refusal / false-positive rates).

## Deployment implications
For LLM agents that query databases (incl. via MCP/tool invocation), constraint-aware inference-leakage defense is a distinct requirement from generic content safety. A single aligned model can replace multi-expert pipelines, improving latency/cost — but the constraint set must be curated per database.

## Monitoring and incident implications
Track cross-turn query correlations that could reconstruct restricted joins/differences (name↔sensitive-attribute); log Safe(x) rejections and their rationale for audit. Watch for prompt-injection and progressive-targeting patterns in NL→SQL logs; treat schema/constraint updates as security-relevant changes.

## Applicability boundaries
Applies to LLM-based Text-to-SQL / NLIDB deployments with declarable privacy constraints. Generalizes to tool/agent settings that expose structured data. It should NOT be assumed to catch leakage paths outside the predefined constraint set, nor to hold against adaptive attackers who probe the detector, nor to transfer unchanged to real enterprise schemas (evaluated on synthetic data). Not a differential-privacy guarantee.
