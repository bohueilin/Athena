## Research question
Can privacy-preserving (secure two-party, 2-PC) Transformer inference be scaled to Mixture-of-Experts (MoE) models WITHOUT (a) leaking which expert a token activates to the server, or (b) losing MoE sparsity by evaluating all experts obliviously?

## Problem definition
In 2-PC PPML, the server homomorphically computes linear/FFN layers on its plaintext weights while the client's input stays encrypted. Under sparse MoE, choosing plaintext expert weights before computation reveals the activated expert to the server — a token-level privacy leak (an access-pattern side channel). Naively evaluating all experts to hide the choice nullifies sparsity and reintroduces the overhead MoE exists to avoid. Existing PPML frameworks (Iron, BumbleBee) target small models (BERT, GPT-2, up to LLaMA-7B) and grow linearly with block count.

## System or model being studied
SecMoE, a 2-PC privacy-preserving inference framework built on lattice-based additive homomorphic encryption + additive/boolean secret sharing (following BumbleBee primitives). Core technique "Select-Then-Compute": (selection phase) unify each expert's per-entry circuit so all entries share one circuit, then obliviously select the chosen expert's parameters via an encrypted one-hot selection vector (B2A-converted, homomorphically applied); (compute phase) evaluate only ONE encrypted expert with ciphertext-ciphertext matmul. Same pattern applied to piecewise-polynomial nonlinearities (secure GeLU): pad segments into uniform entries, obliviously select the active segment's coefficients, evaluate one low-degree polynomial in ciphertext.

## Threat model
- Adversary objective: learn the counterparty's private information — server curious about client's input tokens (incl. which expert is selected); client curious about server's model weights.
- Adversary knowledge: protocol is public; each party sees its own shares/ciphertexts (gray-box on the other party's secret).
- Adversary access: legitimate protocol participant (two-party).
- Adversary capabilities: SEMI-HONEST (honest-but-curious) — both parties follow the protocol but try to extract unauthorized information. Malicious (deviating) adversaries are NOT covered.
- Attacker budget: bounded by cryptographic hardness (lattice/LWE) assumptions; no explicit query budget.
- Phase: inference (private serving).
- Targeted / untargeted: n/a (confidentiality, not integrity).
- Digital / physical: digital.
- Adaptive / non-adaptive: static semi-honest model; no adaptive protocol deviation modeled.

## Trust assumptions
Semi-honest both parties; trusted setup NOT required (paper explicitly excludes CrypTen-based baselines MPCFormer/SHAFT because they rely on a trusted dealer). Security/correctness proofs deferred to Appendix (not in extracted text). Cryptographic assumptions of the lattice-based HE scheme are trusted.

## Attack or failure mechanism
The leakage being closed: expert-selection access pattern. When the server applies plaintext expert weights, it learns the top-k routing decision, which is token-dependent and thus leaks client input semantics. SecMoE keeps the selection encrypted end-to-end so only one expert is computed without revealing which.

## Proposed defense or method
Select-Then-Compute for (1) secure sparse MoE — oblivious ciphertext selection of expert parameters + single-expert ciphertext evaluation, preserving sparsity while hiding routing; (2) secure piecewise-polynomial nonlinearity (GeLU) — oblivious coefficient selection + single low-degree polynomial evaluation. Communication reductions via avoiding redundant expert computation.

## Datasets and benchmarks
Two MoE models (MoE-Small and Switch-Base) under 5 expert settings; expert counts Nexp in {8,16,32,128}, Kexp=1 selected. Evaluated under LAN and WAN. Accuracy compared against a plaintext floating-point baseline (GLUE-style tasks referenced via Wang et al. 2018). Full accuracy tables truncated in extracted text.

## Evaluation methodology
End-to-end latency and communication vs SOTA baselines Iron (Hao et al. 2022) and BumbleBee (Lu et al. 2023) across expert counts and network settings; per-component analysis of secure GeLU. Nimbus excluded due to ~30GB client RAM demand for MoE; trusted-dealer frameworks excluded.

## Metrics
End-to-end runtime (LAN/WAN), communication volume (bytes/MB), speedup and communication-reduction ratios, task accuracy vs plaintext.

## Main findings
Author claims (under evaluated conditions): private inference scales to 63x larger model with only 15.2x end-to-end runtime increase; communication reduced 1.8–7.1x and 1.3–3.8x speedup vs SOTA under 5-expert settings; broader results up to 29.8x communication reduction and up to 16.1x end-to-end speedup vs Iron/BumbleBee; latency stays roughly flat as Nexp grows (5.67–11.24x lower than Iron, 1.13–2.43x over BumbleBee), advantage widening with expert count. Secure GeLU: up to 7.1x speedup and up to 81% communication reduction (Switch-Base, 128 experts). Claimed first practical 2-PC protocol for secure MoE inference.

## Negative results
Could not test >128 experts (256+) due to out-of-memory from loading parameters and storing Beaver-triple correlations. On-demand RAM loading for large MoE left as future work. Ciphertext-ciphertext matmul adds fixed overhead (invoked twice) — beneficial only once it beats evaluating Nexp-1 redundant experts.

## Limitations stated by the authors
Memory ceiling limits expert count; on-demand parameter loading unsolved; comparison scope limited to non-trusted-dealer, RAM-feasible baselines.

## Additional limitations identified during review
_(reviewer synthesis — not author claims)_
- Semi-honest only: a malicious server that deviates (feeds crafted ciphertexts, tampers with masks) is out of scope — real deployment against an actively-adversarial provider is not covered.
- Gating/router side channels beyond expert index (e.g., timing, memory-access patterns of the single selected expert) are not analyzed; leakage claims rest on the ideal-functionality abstraction, with proofs only in the (unextracted) Appendix.
- No end-to-end LLM-quality evaluation on modern large MoEs; accuracy tables truncated here.
- Does not address model-extraction by a semi-honest client accumulating many queries, nor membership inference on training data.

## Design implications
Directly relevant to protecting agent prompt/context confidentiality when inference is offloaded to an untrusted server: routing decisions in sparse models are themselves sensitive metadata. Guardrail/broker designs that split model execution must treat access-pattern leakage (which expert/tool/branch fired) as a first-class confidentiality asset, not just the payload.

## Implementation implications
Oblivious selection of one-of-N branches (experts, polynomial segments, and by analogy tool/skill choices) can be made access-pattern-hiding via encrypted one-hot selection + single-branch ciphertext evaluation — a pattern reusable for confidential tool routing.

## Evaluation implications
Sets a scaling-vs-privacy baseline (communication and latency as functions of branch count) that MoE-serving privacy work should report under both LAN and WAN.

## Deployment implications
Semi-honest, 2-PC, memory-bound: suitable for a controlled two-party confidential-inference service, NOT for adversarial multi-tenant serving or malicious-server threat models. Beaver-triple/parameter memory is the deployment bottleneck.

## Monitoring and incident implications
Because the server learns nothing about routing, server-side monitoring/telemetry of expert usage is intentionally blinded — a tension for defenders who also want auditability; incident forensics on the client side only.

## Applicability boundaries
Applies to: confidential 2-PC inference of sparse-MoE Transformers against honest-but-curious counterparties. Do NOT generalize to: malicious-adversary security, protection against model extraction/membership inference, multi-party (>2) settings, or as a defense against prompt injection / tool abuse (orthogonal — this is confidentiality, not integrity or authorization).
