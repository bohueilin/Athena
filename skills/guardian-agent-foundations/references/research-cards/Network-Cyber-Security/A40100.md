## Research question
How can LLMs be fine-tuned and served over distributed private-data silos on resource-constrained clients while (1) preventing reconstruction of client input from transmitted activations/gradients, (2) avoiding the high communication cost of sequential auto-regressive split learning, and (3) adapting the model split point to task/hardware?

## Problem definition
Federated split learning (e.g., FL-GLM) keeps input/output blocks on the client and offloads middle blocks to a server, but: (1) transmitted mid-layer activations and their gradients can be reverse-engineered to reconstruct the original input (privacy leakage); peer-to-peer key encryption is insufficient because a curious server colluding with a malicious peer client can still infer private data; (2) auto-regressive generation forces a full client-server round trip per token, exploding communication; (3) fixed partition points do not adapt to downstream tasks or device capacity.

## System or model being studied
FedSEA-LLaMA, a Secure/Efficient/Adaptive federated split framework on LLaMA2. Client holds first p blocks (BlocksA) and last q blocks (BlocksC); server holds the middle k blocks (BlocksB). Three mechanisms: (1) Privacy — inject Gaussian noise N(0,delta) into the client's forward-pass hidden state hA before transmission (they show noise on forward activations propagates to gradients too, and is more training-stable than noising gradients, which diverged to NaN); (2) Efficiency — attention-mask compression (transmit only seq_len/pad_len metadata instead of full mask tensors, MB->B) and collaborative KV-cache to avoid retransmitting/recomputing past tokens; (3) Adaptivity — user-tunable number of input/output blocks per task and compute budget. Fine-tuning uses LoRA.

## Threat model
- Adversary objective: reconstruct another client's private input text from the hidden states it transmits (a model-inversion / input-reconstruction attack).
- Adversary knowledge: GRAY-box — adversary knows the client-side model architecture and layer count/depth, but NOT the actual client parameters; initializes an attack decoder of matching architecture/depth.
- Adversary access: an honest-but-curious server COLLUDING with a malicious client; the malicious client shares its own private data in plaintext with the server so the server can train the attack decoder; the server then runs the decoder on victim clients' transmitted hidden states without tampering (stealthy).
- Adversary capabilities: passive observation + local attack-model training; does not alter honest clients' forward results (stealthy inversion). Multi-client (two-client demonstrated) setting.
- Attacker budget: bounded by the malicious client's own labeled data used as supervision for the inversion decoder.
- Phase: training AND inference (activations/gradients exposed during both split forward/backward passes).
- Targeted / untargeted: targeted at reconstructing honest clients' inputs.
- Digital / physical: digital.
- Adaptive / non-adaptive: the paper constructs a strong (collusion-based) attack to stress-test defense, but does not iterate an adaptive attacker against the deployed noise level.

## Trust assumptions
Server is honest-but-curious (follows protocol, curious about data, may collude). At least one client may be malicious and collude with the server. Client-side input/output blocks and their parameters are trusted/local. Gaussian-noise injection is assumed sufficient to obscure reconstruction while preserving utility (empirical, not a formal differential-privacy guarantee — no epsilon reported in extracted text).

## Attack or failure mechanism
Split learning exposes mid-layer activations and their gradients over the network. Via reverse engineering (attack decoder), these reconstruct the original input text. Collusion (curious server + malicious client supplying paired plaintext/hidden-state data) lets the server learn an inversion model and apply it stealthily to victims — inspired by Pasquini et al. 2021 "Unleashing the tiger" split-learning inference attacks.

## Proposed defense or method
Forward-pass Gaussian noise injection on client hidden states hA (shown analytically to perturb downstream gradients of Wn as well), chosen over gradient-noise (which destabilized training). Claimed to protect both forward and backward transmitted quantities while maintaining task performance. Efficiency mechanisms are orthogonal to privacy.

## Datasets and benchmarks
SuperGLUE (NLU, 8 tasks), CoQA (conversational QA, 8k+ dialogues), XSum (abstractive summarization of BBC news). Baseline centralized LLaMA2 and prior FL-GLM. Privacy evaluated via the constructed model-inversion attack.

## Evaluation methodology
Compare task performance vs centralized LLaMA2; measure training/inference speedups and token-generation-time reduction; analyze privacy under the collusion-based inversion attack across partition points; ablations on partitioning. Some results/tables truncated in extracted text.

## Metrics
Task metrics (SuperGLUE accuracy, CoQA QA, XSum ROUGE — ROUGE referenced via Lin 2004); efficiency: up to 8x training/inference speedup, 87.6% average token-generation-time reduction (gain grows with context length); privacy: quality/success of reconstruction under attack (qualitative in extracted text).

## Main findings
Author claims (under evaluated conditions): FedSEA-LLaMA maintains performance comparable to centralized LLaMA2 while achieving up to 8x training/inference speedup and 87.6% lower average token-generation time; forward-pass Gaussian noise yields stable training (gradient-noise diverges to NaN) and reduces the effectiveness of the input-reconstruction attack; adaptive partitioning balances performance vs efficiency across tasks/hardware.

## Negative results
Gradient-noise injection caused training instability/divergence (NaN) — explicitly rejected in favor of forward-activation noise. (Other negative results in truncated experiment section.)

## Limitations stated by the authors
Peer-to-peer key encryption alone is insufficient against server-client collusion (motivating the design). Broader stated limitations not captured in the extracted text.

## Additional limitations identified during review
_(reviewer synthesis — not author claims)_
- No FORMAL privacy guarantee: Gaussian noise is empirical obfuscation, not calibrated (epsilon,delta)-DP in the extracted text; robustness to a stronger/adaptive inversion attacker who tunes to the known noise variance is not demonstrated.
- Privacy-utility tradeoff of noise magnitude delta vs task accuracy is not quantified in the extracted portion.
- Threat model is honest-but-curious; a malicious server that tampers with returned hidden states (integrity/backdoor) is out of scope.
- Attack evaluated with a two-client setup and one attack architecture; generalization to many colluding clients or different decoder capacities untested.
- Efficiency mechanisms (KV-cache collaboration) may themselves widen the leakage surface (more cached state shared) — interaction with privacy not analyzed.

## Design implications
Core-adjacent to agent security: when an agent's inference is split across trust boundaries, intermediate activations/embeddings are recoverable and must be treated as sensitive as the raw prompt. Collusion between an offloading server and a co-tenant is a realistic multi-tenant agent-hosting threat. Perturbing forward activations (not gradients) is the more training-stable lever.

## Implementation implications
Prefer forward-activation perturbation over gradient noise for stability; compress non-sensitive control metadata (attention masks) instead of transmitting full tensors; collaborative KV-cache reduces per-token round trips in split auto-regressive serving.

## Evaluation implications
Any split/federated LLM privacy claim should be stress-tested with a collusion-based model-inversion attack (curious server + malicious client), across partition points — not just with peer eavesdropping.

## Deployment implications
Fits resource-constrained on-device/enterprise-silo LLM fine-tuning where the server is semi-trusted. NOT a defense against a fully malicious server or against integrity/backdoor attacks; lacks a formal DP budget, so residual reconstruction risk is empirical.

## Monitoring and incident implications
Because inversion is stealthy (honest clients' outputs unchanged), detection is hard; defenders should monitor for a server/client requesting paired plaintext+activation data (the collusion setup) and log partition-point/noise configuration for audit.

## Applicability boundaries
Applies to: federated split learning/inference of LLMs on constrained clients under honest-but-curious server + possible client collusion. Do NOT generalize to: malicious-server integrity attacks, formal DP guarantees, or non-split centralized serving. This is privacy-preserving LLM systems work — directly transferable to confidential agent-context handling but not itself an agent-authorization/guardrail mechanism.
