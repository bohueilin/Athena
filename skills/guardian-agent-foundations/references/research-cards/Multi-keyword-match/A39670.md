## Research question
Can CKKS approximate bootstrapping be leveraged to enable **fully encrypted, non-interactive (no client-server round trips) end-to-end training** of real-valued multi-layer perceptrons directly on encrypted data, at practical cost?

## Problem definition
Homomorphic Encryption (HE) enables computation on encrypted data but constrains ML training via (i) noise growth in LHE ciphertexts, (ii) high cost of homomorphic ops, and (iii) limited supported operations. Prior encrypted-training work was limited to logistic regression, last-layer fine-tuning, integer-quantized schemes (BGV/BFV/TFHE), or interactive re-encryption protocols. No prior framework did fully-encrypted non-interactive real-valued DNN training with CKKS.

## System or model being studied
ReBoot — an open-source (OpenFHE/Python) framework for encrypted MLP training under CKKS. Components: (1) a **packing strategy** exploiting CKKS SIMD batching (repeated/expanded/row-/column-wise matrix encodings) that fixes rotation keys and avoids repacking; (2) an **HE-compliant MLP architecture** minimizing multiplicative depth — second-degree polynomial ReLU approximation (EncryptedPolyReLU), residual-sum-of-squares (RSS) loss whose gradient adds no multiplicative depth and matches the cross-entropy gradient under sigmoid, and **local-loss blocks** (layer-wise local classifiers) that confine gradient propagation to limit noise and enable parallel block training; (3) an **encrypted learning algorithm** with HE-compatible Nesterov Accelerated Gradient (momentum + weight decay) and periodic approximate bootstrapping to refresh ciphertext levels.

## Threat model
- Adversary objective: learn the confidential training data (and/or model) processed in an untrusted computing environment (e.g., cloud / ML-as-a-service).
- Adversary knowledge: standard HE/cryptographic setting — the compute host is honest-but-curious (sees ciphertexts, public key, computation) but lacks the secret key. (The paper frames this as "secure data processing in untrusted environments" rather than a formal game.)
- Adversary access: full access to ciphertexts and homomorphic computation; no secret key.
- Adversary capabilities: passive observation of encrypted computation; the paper relies on CKKS/RLWE (Ring-LWE) hardness and cites the Homomorphic Encryption Standard for parameter security level λ.
- Attacker budget: bounded by the RLWE security level implied by encryption parameters Θ = {N, q, Δ}; specific λ not quantified in the extracted body.
- Phase: training (and by extension inference) performed entirely on encrypted data.
- Targeted / untargeted: not applicable (confidentiality, not integrity/evasion).
- Digital / physical: digital.

## Trust assumptions
Client holds the secret key and encrypts inputs/labels; the server/computation environment is untrusted-but-honest (performs the prescribed homomorphic circuit). Post-quantum confidentiality is inherited from RLWE-based CKKS. Non-interactive design removes the trust/latency cost of re-encryption round trips used by prior interactive CKKS training.

## Attack or failure mechanism
Not an attack paper. The "failure" it prevents is data exposure during outsourced computation; the technical failure it engineers around is ciphertext noise corruption after too many multiplications (mitigated by bootstrapping + depth-minimized architecture).

## Proposed defense or method
Confidential computation via CKKS FHE with bootstrapping. Defense-relevant primitives: end-to-end encryption of data during training (confidentiality), non-interactive protocol (reduced exposure/attack surface vs. re-encryption), architecture co-designed to stay within HE constraints.

## Main findings
- Author claim: ReBoot is the first framework for fully-encrypted, non-interactive training of real-valued MLPs with CKKS bootstrapping.
- Author claim: +6.83% test accuracy and up to 8.83× lower training latency vs. prior encrypted-training approaches, on image and tabular benchmarks.
- Author observation: doubling polynomial degree N more than doubles latency; for fixed N, latency is nearly constant across the tested architectures.

## Additional limitations identified during review
_(reviewer synthesis — not author claims)_
- CKKS is an **approximate** scheme; the literature (e.g., Li et al. CRYPTO 2022, cited) notes CKKS is vulnerable to passive key-recovery via approximate-decryption results unless mitigations (e.g., DP/noise flooding) are applied. The paper does not discuss whether ReBoot's outputs/decryptions are safe against this IND-CPA^D class of attack — a real confidentiality caveat for deployment.
- Threat model is honest-but-curious only: no integrity/verifiability against a malicious server that deviates from the circuit (no verifiable computation). A cheating server could return wrong results undetected.
- Local-loss blocks change training dynamics; whether accuracy holds for deeper/non-MLP models is untested.
- Security level λ for the chosen {N, q, Δ} is not explicitly quantified in the extracted body.

## Design implications
For agent/AI-systems security: a concrete, current data point that end-to-end confidential ML training in an untrusted environment is feasible for small models, and that architecture must be co-designed with the crypto (depth minimization, polynomial activations, local losses). Relevant to any design that must process sensitive data (user_data, training_data, model_weights) on infrastructure the operator does not trust — the confidentiality-preserving alternative/complement to TEEs, DP, and federated learning.

## Implementation implications
If adopting HE for confidential agent-side training/inference: budget for the latency scaling with polynomial degree; treat the approximate-decryption (IND-CPA^D) caveat seriously and add noise-flooding/DP on released values; do not assume integrity — pair with verifiable computation if the host may be malicious.

## Evaluation implications
Encrypted-training claims should report the plaintext–encrypted accuracy gap, the concrete CKKS security level λ, and whether released decryptions are protected against approximate-decryption attacks — not only speed/accuracy vs. plaintext.

## Deployment implications
Suitable for confidentiality against a passive honest-but-curious host for MLP-scale workloads; not a defense against a malicious (result-tampering) host and not automatically safe against CKKS approximate-decryption leakage without additional mitigation.

## Monitoring and incident implications
HE hides data from the host, which also reduces host-side observability; incident response must occur client-side after decryption. No runtime integrity signal is provided by HE alone.

## Applicability boundaries
_(where these findings should and should NOT be generalized)_
**Adjacent** to agent security: a privacy-enhancing cryptographic technique (confidential computation) transferable to protecting sensitive data/weights in outsourced AI pipelines.
