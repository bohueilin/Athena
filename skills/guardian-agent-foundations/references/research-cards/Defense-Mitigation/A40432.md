## Research question
Between intra-class and inter-class protection, which is more critical for safeguarding a proprietary RAG knowledge
base, and can *joint* protection of both attack paths provide stronger defense against black-box knowledge-base
extraction than either alone — without degrading answer quality or efficiency?

## Problem definition
RAG systems over proprietary knowledge bases are vulnerable to reconstruction/extraction attacks: a black-box
adversary aggregates responses to crafted queries to rebuild a "proxy" knowledge base and clone the service. Attacks
use two paths — intra-class (iteratively deepen extraction within a topic) and inter-class (recursively expand queries
to semantically-related topics), ultimately achieving near-complete coverage (e.g., RAG-Thief's agent-based memory
loop). Existing defenses protect only one path, and the two known defenses conflict: inter-class distance-thresholding
forces focus on few chunks, while intra-class summarization requires aggregating across many chunks.

## System or model being studied
Standard RAG pipeline (dense retriever + LLM generator) over domain-specific proprietary knowledge bases. Evaluated
generators: Qwen-14B, DeepSeek-R1-8B, Gemma-3-27B. Retriever uses Sentence-BERT-style embeddings; RAGFort adds a
contrastive-reindexed retriever and a draft+reference cascade generator.

## Threat model
- Adversary objective: reconstruct the *entire* underlying knowledge base (not individual private records) to build a
  functionally-equivalent proxy RAG service (IP theft / commercial replication).
- Adversary knowledge: black-box — API query access only; no access to retriever/DB/model internals. (Matches
  commercial/enterprise RAG deployments.)
- Adversary access: crafted/paraphrased queries; adaptive querying agents that store extracted chunks in memory and
  recursively generate new targeted queries (RAG-Thief; Worm-Attack / Cohen et al. jailbreak-style extraction).
- Adversary capabilities: intra-class deepening + inter-class topic expansion; iterative memory-driven query refinement.
- Attacker budget: unbounded black-box queries (iterative); specific query counts not fully visible in extracted text.
- Phase: inference / deployment (query-time extraction).
- Targeted / untargeted: systematic full-KB extraction (both targeted chunk retrieval and broad coverage).
- Digital / physical: digital.
- Adaptive / non-adaptive: attackers are adaptive (agent-based); however an attacker specifically adapting to RAGFort's
  reindexing/cascade is not evaluated in the visible text.

## Trust assumptions
Defender is the system provider with full pipeline access (retriever, DB, LLM). Legitimate users must retain answer
quality. Assumes topic structure is learnable (HDBSCAN clusters) and that a stronger reference model can reliably
judge/replace "high-risk" tokens proposed by the draft model.

## Attack or failure mechanism
Knowledge-base extraction: adversaries piece together fragments returned across many crafted queries. Intra-class
attacks refine queries within a topic to recover precise chunk content; inter-class attacks leverage already-extracted
knowledge to jump to semantically-related topics, propagating until near-complete KB coverage. Single-path defenses
fail because the unprotected path still leaks; and the two existing defenses are mutually conflicting.

## Proposed defense or method
RAGFort — a structure-aware dual-module defense:
- Inter-class isolation via contrastive reindexing: (1) HDBSCAN unsupervised clustering of Sentence-BERT chunk
  embeddings to assign pseudo topic-labels; (2) supervised contrastive (SupCon) training of a tokenizer-aligned
  encoder to widen inter-topic margins; (3) rebuild the dense retriever index with these embeddings (query encoder and
  generator input pipeline unchanged, so generation quality is preserved). This makes cross-topic query expansion
  harder.
- Intra-class protection via constrained cascade generation: a lightweight draft model proposes tokens; a stronger
  reference/verifier model selectively filters or replaces high-risk/sensitive tokens using an efficient rejection
  rule `π = (1−r)·q_t + r·p_t` with a rejection budget B and a sensitivity threshold C, with a claimed theoretical
  near-optimality guarantee. This suppresses precise sensitive-content emission while preserving inference efficiency.
The paper first runs a masking experiment showing joint (both-path) protection degrades the proxy KB far more than
either single path — motivating the dual design.

## Datasets and benchmarks
HealthCareMagic (medical QA), Enron Email, and Math QA (MathQA), each used to build an independent proprietary KB.
Attacks evaluated: RAG-Thief and Worm-Attack (Cohen et al. 2024). Baseline defenses: re-ranking, summarization, and
Set Distance Threshold (Zeng et al. 2024a).

## Evaluation methodology
Three axes: security (Chunk Recovery Rate under RAG-Thief and Worm-Attack), system performance (Answer ACC + FLOPs
before/after protection, Table 3), and ablation (RAGFort-InterOnly vs. RAGFort-IntraOnly vs. full). Masking experiment
validates the complementarity hypothesis across the three domains.

## Metrics
- Chunk Recovery Rate (CRR) — proportion/number of KB chunks recovered by the attacker (lower = stronger protection);
  reported both absolute and as "Relative Mean CRR" (× of original/no-defense).
- Answer Accuracy (ACC, %) — utility preservation.
- FLOPs (T) — generation efficiency/overhead.

## Main findings
- Author claim + visible numbers: full RAGFort achieves the lowest CRR across both attacks, reducing Relative Mean CRR
  to 0.51× of the undefended baseline, vs. re-ranking 0.91× and summarization 0.87× (substantially weaker).
- Ablation (visible): under RAG-Thief, full RAGFort reduces CRR from 57.16% to 27.96% (HealthCareMagic, Qwen-14B),
  while single-module variants still expose >40%; averaged relative mean CRR — full 0.51× vs. InterOnly 0.75× vs.
  IntraOnly 0.83× — confirming complementarity.
- System performance (Table 3, visible): ACC drop < 2 points after protection (e.g., Qwen-14B HealthCareMagic
  68.16→66.57; DeepSeek-R1-8B 61.36→61.12; Enron near-unchanged ~99→~98.85), and FLOPs unchanged or *reduced* (draft
  model replaces large-model inference; when draft = base model, overhead is negligible).
- Author claim: first systematic study defending against RAG knowledge-base extraction via joint dual-path protection.

## Negative results
Single-module variants are insufficient (still leak >40% chunks under RAG-Thief); a residual CRR (~28% in the shown
cell) remains even with full RAGFort — protection is substantial but not complete. Slight ACC drop attributed to the
draft-vs-original model gap, not the defense itself.

## Limitations stated by the authors
Residual accuracy drop arises from the draft/reference model gap (mitigated by using a stronger draft model). The
paper positions protection as "significantly reduces" reconstruction, not elimination.

## Additional limitations identified during review
_(reviewer synthesis)_
- No adaptive-attacker-aware evaluation: an attacker who knows RAGFort reindexes topics / cascades generation could
  adjust query strategy (e.g., within-cluster probing, paraphrase to dodge the rejection rule); residual CRR (~28%)
  suggests headroom for a stronger adversary.
- HDBSCAN pseudo-labels drive inter-class isolation; poor clustering (overlapping domains, fine-grained topics) could
  weaken margins — sensitivity to cluster quality is not stressed in the visible text.
- The cascade's "sensitive content" judgement depends on the reference model; false negatives leak, false positives
  hurt utility — the C/B thresholds' robustness across domains is not deeply characterized here.
- Three domains only; multilingual / very-large KBs and streaming-updated KBs are untested.

## Design implications
RAG knowledge-base IP protection must cover *both* extraction paths simultaneously — inter-class topic isolation and
intra-class content suppression are complementary, and protecting one path alone leaves the KB extractable. Decoupling
the protected retriever index from the generator's content pipeline preserves answer quality while isolating topics.

## Implementation implications
Contrastive reindexing (retriever-side) + draft/reference cascade with a sensitivity-aware rejection rule
(generator-side) can be added to an existing RAG stack with <2-point ACC cost and no FLOPs increase (often a decrease),
making dual-path defense practical for deployment.

## Evaluation implications
KB-extraction defenses should be measured with agent-based extraction attacks (RAG-Thief, Worm-Attack), report
Chunk-Recovery-Rate (absolute + relative), ablate each path, and jointly report utility (ACC) and efficiency (FLOPs);
future work should add adaptive attackers that target the specific defense.

## Deployment implications
Directly applicable to commercial/enterprise RAG services exposing only a query API: treat the knowledge base as a
protected asset/IP, add retrieval isolation + output filtering, and monitor for extraction-style query patterns.
Protection is a strong mitigation, not a guarantee — residual leakage remains, so pair with rate-limiting and query
monitoring.

## Monitoring and incident implications
Log per-session chunk-coverage / topic-jump patterns; agent-style extraction shows recursive topic expansion and
memory-driven query refinement that can be detected. CRR against known attacks is a useful pre-deployment red-team KPI.

## Applicability boundaries
Applies to retrieval-augmented generation over proprietary text knowledge bases under black-box query access. It is a
KB-*extraction*/IP-theft defense — distinct from per-record membership/attribute privacy — and does not address prompt
injection into retrieved content, poisoning of the KB, or agent tool-abuse. Core to agent/LLM-system security (RAG).
