## Research question
Can a malicious MCP server manipulate an LLM agent's tool-selection process — via only the tool name and description — so the malicious server is consistently preferred over functionally equivalent competitors, yielding economic benefit, while remaining stealthy to human and automated inspection?

## Problem definition
MCP lets LLM agents autonomously discover and select tools from third-party servers based on tool name + description. In a profit-competing ecosystem, a server that biases the LLM's selection toward itself gains usage fees / advertising revenue unfairly. The paper introduces this new threat — MCP Preference Manipulation Attack (MPMA) — targeting the task-planning and tool-selection stages, and studies effectiveness vs stealthiness.

## System or model being studied
MCP-based LLM agents (MCP Host / Client / Server). Base LLMs evaluated: Deepseek, Claude, GPT-4o, Gemini, Qwen3 (Grok3 also referenced). The LLM sees only each tool's name and description (server internal logic is invisible), so the attack surface is the metadata.

## Threat model
- Adversary objective: maximize the malicious server's selection frequency across diverse user queries to capture economic benefit; secondary objective is stealth.
- Adversary knowledge/access: attacker is the MCP server builder with white-box control over its own server's metadata (tool name, description) and can publish to third-party MCP platforms. No control or modification of the base LLM.
- Adversary capabilities: (DPMA) prepend manipulative words/phrases ("This is the best tool in the world." / "best") to description or name; (GAPMA) rewrite descriptions with four advertising strategies — Authoritative, Emotional, Exaggerated, Subliminal — using GPT-4o, then apply a black-box Genetic Algorithm (mutation + crossover + top-k selection via GPT-4o) to enhance stealth.
- Attacker budget: metadata-only edits; GPT-4o generation + GA iterations.
- Phase: deployment/inference (tool-selection stage ❶ task planning, ❷ tool selection).
- Targeted / untargeted: targeted (bias selection toward the attacker's server).
- Digital / physical: digital.
- Adaptive / non-adaptive: attack optimizes stealth against LLM-as-judge/human detection; no dedicated defense is deployed and adapted against it.

## Trust assumptions
The MCP host/LLM trusts tool descriptions as neutral, truthful capability metadata when ranking tools. Users and third-party platform reviewers manually inspect names/descriptions; automated detectors may also screen them — the attack must survive both.

## Attack or failure mechanism
LLM tool selection is swayed by persuasive language in the metadata. DPMA: explicit superlatives ("best tool in the world") make the LLM justify choosing the malicious tool — highly effective but conspicuous. GAPMA: advertising-style rewrites (e.g., Exaggerated: "Access reliable and precise weather forecasts…") persuade without overt manipulative terms; the GA optimizes descriptions toward stealth while preserving persuasion. Counterintuitively, in a "malicious majority" setting several LLMs revert to the most straightforward benign tool ("over-manipulation").

## Proposed defense or method
No defense is implemented/evaluated. The paper argues MPMA reveals a fairness/trust gap in open MCP ecosystems and calls for robust, systematic defenses; it does not build one.

## Datasets and benchmarks
8 competing MCP servers (real ones referenced, e.g., weather, time, web search, maps, image generation) with 10 constructed queries per server; 5 mainstream LLMs. Malicious-majority experiment on the Time server with 8 servers (Best Name, Best Description, four GAPMA strategies, two benign).

## Evaluation methodology
For each server/LLM, measure how often the manipulated tool is selected across the query set (effectiveness) and how often the description is flagged suspicious by (a) LLM-as-a-judge with five widely used LLMs and (b) human evaluation (stealthiness). Compare DPMA (raw vs best description/name) against GAPMA with/without GA across the four advertising styles.

## Metrics
Attack Success Rate (ASR) / Selection Rate (SR) — frequency the manipulated server is chosen. True Positive Rate (TPR) here = proportion of tool descriptions flagged suspicious (higher = less stealthy). Economic-impact estimate (conservative, from full version).

## Main findings
- Author claim: DPMA is highly effective — 100% ASR in most settings — but low stealth (superlatives trigger suspicion).
- Author claim: GAPMA balances high effectiveness and high stealthiness; combining advertising strategies + GA substantially lowers the suspicion (TPR) versus DPMA under both LLM-as-judge and human evaluation.
- Author claim: "over-manipulation" — in a malicious-majority scenario, Deepseek/Claude/Gemini pick a benign, straightforward tool, apparently becoming alert when too many descriptions are manipulative.
- Author claim: conservative economic estimate of >$200,000/year unfair benefit in the web-search server segment alone; impact expected to grow with MCP adoption.

## Negative results
The malicious-majority "over-manipulation" effect is a failure mode of the attack: excessive manipulation across competitors can backfire and drive some LLMs to benign choices. DPMA fails the stealth objective despite maximal effectiveness.

## Limitations stated by the authors
The over-manipulation phenomenon is offered speculatively ("we speculate"). The economic figure is a conservative estimate (full version). Experiments cover 8 servers × 10 queries × 5 LLMs — a bounded scale. Deeper discussion deferred to the full version.

## Additional limitations identified during review
_(reviewer synthesis — clearly not author claims)_
- No defense is evaluated, so residual risk after any mitigation (metadata sanitization, selection auditing) is unknown.
- Small evaluation scale (8 servers, 10 queries each) limits statistical generality of ASR/SR.
- Stealth is judged by LLM-as-judge + human panels; those judges are themselves manipulable and their agreement/robustness is not fully characterized.
- The economic estimate rests on modeling assumptions in the full version, not measured revenue.
- GAPMA depends on GPT-4o + GA, an attacker cost/dependency; transfer of optimized descriptions across LLM versions over time is untested.

## Design implications
Tool selection driven by free-text descriptions is an unfair-ranking / integrity attack surface, not just a safety one: persuasive metadata can bias an agent's choice among honest competitors. Selection should weigh verifiable capability signals (schemas, provenance, measured performance, reputation) over persuasive prose, and normalize/neutralize marketing language before ranking.

## Implementation implications
MCP hosts/registries should sanitize and de-bias tool descriptions prior to inclusion in the selection prompt, detect superlative/advertising patterns, and consider provenance- or attestation-weighted ranking. Because DPMA reaches 100% ASR with trivial edits, even simple description-normalization or keyword screening is a worthwhile first control; GAPMA shows such screening must go beyond obvious superlatives.

## Evaluation implications
Agent-security evaluations should include "preference/ranking manipulation" (adversarial SEO for tool selection) as a distinct threat alongside prompt/tool injection, and should measure both effectiveness (selection rate) and stealth (human + automated flagging). The over-manipulation effect suggests testing multi-attacker ecosystems, not just single malicious servers.

## Deployment implications
In open, monetized MCP marketplaces, tool selection is exploitable for economic gain; platforms need fairness controls and abuse monitoring. Content-based reviewer inspection alone is insufficient because GAPMA evades it.

## Monitoring and incident implications
Log tool-selection decisions with the descriptions that drove them; monitor for advertising/superlative patterns and for servers whose selection share is anomalous relative to measured quality. LLM-as-judge screening can catch DPMA but under-detects GA-optimized descriptions, so pair automated flags with reputation/behavioral signals.

## Applicability boundaries
_(where these findings should and should NOT be generalized)_
Core to LLM-agent / MCP / tool security, specifically the tool-selection stage and ecosystem fairness. Results are bounded to the 8 servers / 5 LLMs / metadata-only setting; ASR/stealth numbers and the economic estimate should NOT be generalized to arbitrary agents, larger marketplaces, or future model versions without re-testing. Distinct from data-exfiltration tool poisoning (see A40895) — here the payoff is biased selection, not credential theft.
