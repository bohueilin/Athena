## Research question
How can multi-agent AI for industrial asset operations be evaluated online in a competition setting that is reproducible and gives actionable diagnostics, while preserving the confidentiality of industrial data and hidden evaluation scenarios (i.e., without exposing raw trajectories or underlying data to participants)?

## Problem definition
Industrial multi-agent AI is hard to evaluate: tasks are complex and data is confidential, limiting data sharing; competition platforms like Kaggle return only scores (no "why it failed"), reducing engagement and increasing dropout. Existing agent benchmarks focus on planning/trajectory analysis and lack infrastructure for code-oriented, reproducible evaluation in applied industrial domains under privacy constraints.

## System or model being studied
AssetOpsBench-Live: a competition-ready evaluation platform integrating AssetOpsBench (6-dimension multi-agent scoring + automated failure-mode discovery) with Codabench (reproducible, code-oriented competitions). Participants validate agents locally against a simulated environment (CouchDB-backed, Docker-distributed: IoT Agent with 7 tools, FMSR Agent with 3 tools, TSFM Agent with 5 tools, Work Order Agent with 8 business objects), then submit containerized code (one .py + one .json) that runs on one public plus several hidden industrial scenarios. The system returns scores and clustered failure modes rather than raw trajectories.

## Threat model
- Adversary objective: (implicit) a competition participant learning/extracting the hidden industrial scenarios, raw sensor data, utterances, or server-side trajectories that must remain confidential.
- Adversary knowledge (white/gray/black-box): participants have the public scenario and simulated environment (white-box locally) but only aggregated scores + clustered failure categories for hidden scenarios (black-box to the confidential data).
- Adversary access: submit containerized code executed server-side on hidden scenarios; receive categorized diagnostic reports.
- Adversary capabilities: iterative resubmission; craft submissions that might probe or exfiltrate hidden data via outputs/logs (paper's design withholds raw traces to prevent this).
- Attacker budget: not stated in paper (competition with 225 users / 300+ evaluations reported).
- Phase (training / inference / deployment): evaluation/deployment phase of the agent lifecycle.
- Targeted / untargeted: confidentiality of specific industrial scenarios/data.
- Digital / physical: digital platform over industrial (sensor/IoT) data.
- Adaptive / non-adaptive: iterative-resubmission loop is adaptive by design; no formal adversarial privacy analysis.

## Trust assumptions
Participant-submitted code is untrusted and is run in a controlled server-side execution environment; participants are not trusted to see raw data, utterances, or hidden scenarios. Submission pre-validation (exactly one .py + one .json with required keys) plus optional human checks gate what executes. LLM-as-Judge is trusted to score six dimensions (with acknowledged subjectivity).

## Attack or failure mechanism
The confidentiality risk is that returning raw execution trajectories would leak industrial data / hidden scenarios to competitors. The paper's core mechanism converts full trajectories into (a) quantitative six-dimension scores and (b) clustered, interpretable failure-mode categories, so participants get "where/why it failed" without receiving underlying data. Separately, the platform diagnoses agent *failure modes* (e.g., reasoning–action mismatch, step repetition, missing clarifying questions, missing-data handling, output-validation and tool-usage errors) — an agent-reliability rather than adversarial concern.

## Proposed defense or method
Privacy-aware evaluation architecture: (1) local Docker-based simulated environment for development/debugging (no access to hidden data); (2) containerized submission executed server-side on public + hidden scenarios; (3) return only scores + dynamically clustered failure modes, never raw trajectories/utterances/data (Algorithm 1: Dynamic Failure Mode Taxonomy — LLM diagnostic over trajectories, match to initial taxonomy, cluster novel failures into new categories). Multi-phase (Bootstrap, Leaderboard), multi-track (Planning/Execution) design; automated pre-validation with optional human checks. Defensive posture = sandboxed execution + output-abstraction/least-exposure + human-in-the-loop gating.

## Datasets and benchmarks
AssetOpsBench (six-dimension multi-agent evaluation) + Codabench platform. Simulated environment with sampled sensor telemetry, work orders, IoT streams, alerts, and failure-mode catalogs; a small reference dataset ships in the Docker image. Hidden, track-specific industrial scenarios remain server-side. Real industrial partner context: Steel Authority of India Limited (co-author affiliation).

## Evaluation methodology
Agents scored via LLM-as-Judge across six dimensions: Task Completion, Accuracy (Retrieval), Result Verification, Action Sequencing, Clarity, Hallucinations — at scenario and model levels. Example run (#371162) aggregated over 11 hidden scenarios; failure-mode clustering surfaced six clusters (worst: handling missing data, then output validation, then tool usage). A motivating diagnostic experiment added clarifying-question support (enable_agent_ask=True) to the open-source ReActXen agent.

## Metrics
Six-dimension LLM-as-Judge scores (illustrative run #371162: Task 6, Retrieval 6, Verification 7, Sequence 8, Clarity 9, Hallucinations 2). Failure-mode analysis: ~10% of multi-agent task failures attributed to missing clarifying questions (from the AssetOpsBench paper). Adding clarifying interactions improved reported task performance: LLaMA-4 Maverick 59%→66% (+7), LLaMA-3-405B 44%→61% (+17). Platform usage: 225 users, 300+ agent evaluations. No privacy-leakage metric or formal privacy guarantee is reported.

## Main findings
Author claims: (1) a working platform delivers reproducible, real-time, privacy-aware evaluation of multi-agent industrial AI by exposing scores + clustered failure modes instead of raw trajectories; (2) actionable diagnostics translate into concrete code-level agent improvements (clarifying-question example produced a leaderboard-topping agent); (3) the system safeguards industrial confidentiality while giving interpretable, iterative feedback, validated by real usage (225 users, 300+ evals).

## Negative results
None framed as failures. Author acknowledges LLM-as-Judge subjectivity (especially "hallucination") as an open weakness affecting metric reliability.

## Limitations stated by the authors
Subjectivity of LLM-as-Judge metrics (notably hallucination) is an open problem; future work extends the platform to broader scenarios and addresses judge subjectivity. Scope is a demo of a system rather than a controlled study.

## Additional limitations identified during review
_(reviewer synthesis)_
- "Privacy-aware" is realized via output-abstraction (withhold raw trajectories) and sandboxing, but the paper provides NO adversarial privacy evaluation — e.g., no test of whether crafted submissions can exfiltrate hidden-scenario data through scores, failure clusters, timing, error messages, or side channels.
- Server-side execution of untrusted participant code is a real attack surface (data access, network egress, resource abuse); the sandbox/isolation design and its guarantees are not detailed.
- Failure-mode clustering itself uses an LLM over confidential trajectories; leakage via cluster labels/descriptions is not analyzed.
- Metrics (6-dimension scores, improvement deltas) depend on an LLM judge whose reliability is self-acknowledged as subjective; no inter-rater/agreement analysis is given.
- Demo-scale evidence (usage counts) is not a controlled privacy or robustness result.

## Reproducibility
- Code available: underlying AssetOpsBench and ReActXen are open-source (GitHub referenced); the Live platform is accessible via Codabench competition link.
- Data available: simulated environment + small dataset shipped via Docker; hidden industrial scenarios intentionally withheld.
- Model available: agents are participant-supplied; evaluation uses LLM-as-Judge (models not fully specified for the judge).
- Configuration completeness: moderate — architecture, submission format, agent/tool counts, and six dimensions are described; sandbox internals, judge model/prompt, and scenario details are not.
- Reproduction difficulty: moderate for using the platform; high for reproducing the confidential evaluation exactly (hidden data by design).
- External dependencies: Codabench, CouchDB, Docker registry, LLM judge, ReActXen.

## Design implications
Directly relevant to agent-evaluation infrastructure: to evaluate agents on confidential data, expose *derived diagnostics* (scores + clustered failure modes) rather than raw trajectories — an output-minimization / least-exposure pattern. Sandboxed server-side execution of untrusted agent code plus pre-validation and optional human gating is a reusable trust-boundary design.

## Implementation implications
Enforce a strict submission contract (exactly one .py + one .json with required keys) and pre-validation before executing untrusted code; run on a public scenario first, then hidden ones; dynamically extend a failure-mode taxonomy via LLM clustering so novel failures are categorized without shipping traces back.

## Evaluation implications
Models a privacy-respecting competition/benchmark: hidden scenarios prevent overfitting/contamination, and actionable failure clusters (vs bare scores) drive iterative improvement. But LLM-as-Judge subjectivity and lack of adversarial-privacy testing are cautions for anyone adopting this as a security-grade evaluation harness.

## Deployment implications
Suitable where industrial data cannot leave the owner's boundary yet external agents must be evaluated; the platform keeps raw data/trajectories server-side. Before security-sensitive deployment, the untrusted-code sandbox and exfiltration-resistance of the diagnostic outputs need hardening/validation not provided here.

## Monitoring and incident implications
Failure-mode clustering doubles as operational monitoring of agent reliability (missing-data handling, output-validation, tool-usage errors). Incident-relevant gaps: no described monitoring for malicious submissions attempting data exfiltration or resource abuse during server-side execution.

## Applicability boundaries
_(where to and NOT to generalize)_
**Core** to agent security: multi-agent LLM systems, tool use, agent-to-agent coordination, evaluation-artifact/industrial-data confidentiality, and LLM-as-Judge — all central agentic concerns. However, "privacy-aware" here means operational data-minimization and sandboxing, NOT a formal privacy guarantee; do not cite it as leakage-proof. The failure-mode taxonomy addresses reliability, not adversarial robustness.
