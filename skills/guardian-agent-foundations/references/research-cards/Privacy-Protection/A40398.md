## Research question
Can LLM unlearning remove specific *source-code* snippets (copyrighted, insecure, or deprecated) without the catastrophic utility collapse that generic sample-level unlearning causes on rigidly-syntaxed programming languages?

## Problem definition
Given a forget set D_f of (prompt, undesirable completion) code pairs, post-train an LLM so it assigns near-zero probability to the undesirable completions while preserving general code-generation ability. Existing sample-level unlearning (GA, NPO, DPO, FLAT) achieves ~90% forgetting but drops code-generation success to near zero (mute refusal, token collapse, syntactic incoherence).

## System or model being studied
Code LLMs: CodeLlama-7B, Qwen2.5-Coder-7B, Deepseek-coder-6.7B, Starcoder-7B. Method PROD (Probabilistic Redistribution for Output Distribution) is a token-level, optimization-based unlearning method.

## Threat model
- Adversary objective: cause the model to emit forgotten/undesirable code (copyright infringement, insecure snippets, deprecated APIs), or recover forgotten code via adversarial attack.
- Adversary knowledge: paper evaluates robustness against "targeted attacks" / prefix-injection-style adversarial prompts (gray/black-box prompting).
- Adversary access: prompt-level (elicit forgotten code); references adversarial frameworks (Yuan et al. 2024, prefix injections).
- Adversary capabilities: craft adversarial prompts to reproduce forgotten code.
- Attacker budget: prompt-level (no weight access assumed for the robustness test).
- Phase: post-training (unlearning) / inference (attack).
- Targeted / untargeted: targeted (specific snippets).
- Digital / physical: digital.
- Adaptive / non-adaptive: an adversarial-attack experiment is run; not described as fully adaptive to PROD's internals.

## Trust assumptions
Defender owns the model and can post-train it. Undesirable snippets need not appear verbatim in training data (D_f merely captures behavior to eliminate). Utility measured on held-out general code benchmarks.

## Attack or failure mechanism
Root cause = *granularity*: sample-level methods down-weight entire undesirable sequences, stripping the shared grammar/scaffolding of programming languages. Three observed failure modes of baselines: Mute Refusal, Token Collapse (repeat "\n", "<SUF>" artifacts), Syntactic Incoherence (uncompilable output).

## Proposed defense or method
PROD manipulates the *token-level output distribution*: (1) collect the LLM's full vocabulary distribution; (2) **forget-data elimination** — zero the probability mass of tokens constituting the undesirable snippet; (3) **noise elimination** — prune long-tail incidental noise; (4) **probabilistic redistribution** — reallocate mass over remaining vocabulary to preserve the model's programming-language statistics; (5) optimize the model to match this sculpted target distribution (loss L_PROD). A benchmark of three tasks (copyrighted / insecure / deprecated-API unlearning) and a **Pareto Dominance Ratio (PDR)** metric jointly scoring forget quality and utility are introduced.

## Datasets and benchmarks
Authors' new source-code unlearning benchmark: copyrighted code, insecure code (CWE-related), deprecated APIs. Utility via a standard code-generation benchmark (HumanEval-style; exact set truncated). Baselines: GA, NPO, DPO, FLAT.

## Evaluation methodology
Measure forget quality (dissimilarity from undesirable completion) and model utility (retained code-gen performance) across four LLMs and three tasks; combine via PDR (Pareto dominance). Additional adversarial-attack experiment tests whether forgotten code can be reproduced.

## Metrics
Forget quality, model utility (code-gen success rate), and PDR (higher = better joint trade-off). Author claim: PROD attains the best PDR across all three tasks and all four LLMs, and is the *only* baseline resilient to targeted attacks without reproducing forgotten code.

## Main findings
- (Author claim) Baselines reach ~90% forgetting but collapse general code-gen to near-zero; PROD forgets while preserving utility (Figure 1/3 cases).
- PROD generalizes across four distinct code-LLM families.
- PROD alone resists the adversarial attack without regenerating the forgotten snippets.

## Negative results
Baselines' near-total utility collapse is the motivating negative result. PROD's own residual forget-quality-vs-utility gap on specific tasks is reported via PDR (exact per-task numbers truncated in extracted text).

## Additional limitations identified during review
_(reviewer synthesis — not author claims)_
- Token-level suppression assumes the undesirable snippet's tokens can be enumerated; paraphrased/semantically-equivalent insecure code (different tokens) may evade forgetting — not clearly quantified.
- "Near-perfect forgetting" is a distributional claim; no weight-level relearning (RTT-style) attack is reported, unlike A40343.
- Only 6.7–7B models; the adversarial test's adaptivity/strength is under-specified in the extracted text.
- Insecure-code unlearning reduces emission of *known* bad snippets but does not certify secure generation.

## Design implications
For structured-output domains (code, and by extension config/DSL/tool-call syntax), unlearning should operate at token-distribution granularity to avoid destroying shared grammar. Redistribution (not just suppression) preserves the "scaffolding."

## Implementation implications
Requires access to full per-step vocabulary logits and a distribution-matching loss; heavier than a simple gradient-ascent loss but avoids collapse. Relevant to agent code-generation pipelines that must suppress licensed/insecure snippets.

## Evaluation implications
PDR (joint forget-vs-utility Pareto scoring) is a transferable idea: never report forgetting without paired utility. Add adversarial reproduction tests.

## Deployment implications
Directly applicable to coding assistants/agents that must avoid emitting copyrighted code, known-vulnerable patterns (CWE), or deprecated APIs. Frame as "reduced emission under the tested threat model," not a security guarantee against all vulnerable code.

## Monitoring and incident implications
Complement with output-time license/secret/CWE scanners; PROD reduces but does not provably eliminate undesirable emissions, so runtime filtering and incident logging remain warranted.

## Applicability boundaries
Applies to optimization-based unlearning of enumerable code snippets in open-weight code LLMs. Does NOT address prompt-injection into coding agents, tool-credential leakage, or closed-API models. Do not generalize "surgical forgetting" to guaranteed secure/legal code generation.
